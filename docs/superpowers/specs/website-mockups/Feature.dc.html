RETRY MECHANISM

Flaky networks shouldn’t fail your suite.

Retry failed requests with a count, a delay and exponential backoff — per request or for the whole file — and choose exactly which status codes deserve another try.

Read the docs Install curl-runner
retry.yaml 
global:
  defaults:
    retry: { count: 3, delay: 1000, backoff: 2 }

requests:
  - name: Flaky upstream
    url: https://api.example.com/data
    retry:
      count: 5
      delay: 2000
      retryableStatuses: [429, 500, 502, 503]

Exponential backoff

Each attempt waits longer than the last, so a struggling server gets room to recover.

Per request or global

Set a default for the file, override it on the one endpoint that needs more patience.

Only the right failures

Retry on 429 and 5xx, never on a 400 your request deserved. Timeouts and dropped connections retry too.

Good for

01Intermittent network failures in CI
02Rate-limited APIs that answer 429
03Services that take a moment to warm up after a deploy
04Smoke tests against shared staging environments
