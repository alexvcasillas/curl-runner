# Postman collection import

Status: draft, 2026-11-03

## Why

People share REST APIs as Postman collections: a JSON file their users import to see every endpoint and what to send. The studio's Import dialog has had a Postman tab marked "Coming soon" since the preview. With an importer, someone with a collection can move to curl-runner in one step, without rewriting each request by hand.

The motivating case is an API team whose collection is generated by a build script and shared with customers. That shape guides the design:

- Collection v2.1, exported from Postman or produced by a script. The two differ only in small details (see Input).
- About 20 requests in one level of folders, most of them `POST`.
- API key auth on the collection, sent as a header and read from a variable. A few requests turn auth off.
- A few collection variables (a base URL, the API key) used in every URL and in many headers. Postman's export marks the API key `"secret": true`.
- Bodies are raw JSON or `multipart/form-data`, with file fields and many text fields.
- Most form fields are disabled. They're optional settings listed so a reader can see them and switch one on.
- Every request has a description. That's where "what to send" lives.
- No scripts, no `{{$dynamic}}` variables, no saved example responses.

Collections from other people will use more of Postman's features, so anything the importer can't convert has to show up in a report, never disappear silently.

## Goals

1. One converter in `curl-runner-core`, shared by the CLI and the studio.
2. A CLI command, `curl-runner convert postman <collection.json>`, that writes a folder of YAML files and a `.env`. It's usable in scripts and CI, so a generated collection can be re-converted on every build.
3. The studio's Postman tab works. You pick a file and a target folder, see what will be written, import, and get a summary.
4. A converted request runs once the user provides its secret values and picks any upload files. Nothing else should be needed.
5. The converted YAML keeps what a reader of the collection relies on: request names, folders, descriptions, and the optional (disabled) fields.

## Non-goals

- OpenAPI import. That's the next round; this round makes Postman solid first.
- Postman environment files (`*.postman_environment.json`). Only collection variables are imported. This is a follow-up candidate.
- Pre-request and test scripts. They're reported, not translated.
- Exporting back to Postman, or keeping a collection and its YAML in sync.
- Postman Collection v1.

## Anti-goals

These would make the feature a failure even if it technically worked:

- A secret value written to any file: YAML, `.env`, logs or the report.
- Overwriting an existing file or environment value.
- Dropping something without saying so. Every unsupported part of the input appears in the report.
- Real-world collections in the repo. Tests use hand-written sample collections only.

## Input

- Accept Collection v2.1 and v2.0 (`info.schema`). They're close enough to share one parser. Reject v1, and any JSON without `info` plus `item`, with a clear message naming the schema found.
- Ignore Postman's export metadata (`info._postman_id`, `_exporter_id`, `_collection_link`).
- `url` may be a string or an object (`raw`, `host`, `path`, `query`, `variable`). Use `raw` when it's present.
- Folders can nest to any depth, even though the motivating case uses one level.
- Request fields to handle: `method`, `header` (including `disabled`), `url.query` (including `disabled`), `body`, `auth`, `description`. `description` may be a string or `{content, type}`.

## Mapping

| Postman | curl-runner |
| --- | --- |
| Folder | Subfolder (name made filesystem-safe) |
| Request | One YAML file named after the request, made filesystem-safe and lowercased, with `.yaml` |
| `{{name}}` anywhere in URL, headers or body | `${name}`, keeping the name as-is |
| Collection `variable[]` | Entries in the target's `.env`. Secret ones are handled as in Secrets below. |
| `variable[].secret: true` | Secret (see Secrets) |
| Request `name` | `name:` |
| Request `description` | `#` comment lines at the top of the file. Requests have no description field. |
| Folder `description` | `#` comment lines at the top of every file in that folder, after the request's own description |
| Collection `description` | A `README.md` in the output root, created only if it doesn't exist |
| `header[]` | `headers:` |
| `url.query[]` | `params:` |
| Path variables (`:id` plus `url.variable[]`) | `${id}` in the URL, with its value in the file's `global.variables`. A request's own `variables:` isn't used for interpolation, so it won't do. |
| `body.mode: raw`, valid JSON | `body:` as JSON. If the language is JSON, also `Content-Type: application/json` unless already set. |
| `body.mode: raw`, not JSON | `body:` as a string, with the language's content type unless already set |
| `body.mode: urlencoded` | `body:` as a urlencoded string, with `Content-Type: application/x-www-form-urlencoded` |
| `body.mode: formdata` | `formData:`. Text fields become values; file fields become `{file: <path>}`. |
| File field with a `src` | `file:` set to that path |
| File field without `src` (Postman's export drops it) | `file:` set to a placeholder path, listed in the report as "pick a file" |
| `body.mode: graphql` | `body:` as JSON `{query, variables}` |
| `body.mode: file` (binary) | Reported, not converted |
| `auth` (`apikey`, `in: header`) | A header with that key and value |
| `auth` (`apikey`, `in: query`) | A query param |
| `auth` (`bearer`) | `auth: {type: bearer, token}` |
| `auth` (`basic`) | `auth: {type: basic, username, password}` |
| `auth` (`noauth`) | No auth. Turns inheritance off for that request. |
| Auth inheritance | Request auth, else the closest folder's, else the collection's |
| Any other auth type (oauth2, digest, aws, ...) | Request converted without auth, and listed in the report |
| `event[]` (scripts) | Reported per request or folder, not converted |
| `{{$guid}}` and other dynamic variables | The matching curl-runner dynamic variable when one exists, otherwise left as written and reported |
| Saved `response[]` examples | Counted in the report, not converted |

### Disabled fields

Disabled headers, query params and form fields come in as commented-out YAML lines in the same place they'd go if enabled, with their description as a comment beside them.

- Uncommenting a line has to give valid YAML at the right indentation, with nothing else to edit.
- A disabled file field is commented out with its placeholder path.

The YAML serializer can't write comments, so this needs a pass after serializing. It must not change any enabled line.

### Variable names

Keep Postman's names (`baseUrl` stays `baseUrl`) so they still match the collection's own docs.

- Valid names use only `[A-Za-z0-9_]`. Any other character (`.`, `:`, `-`, space) becomes `_`.
- A name that collides with something curl-runner treats specially gets a suffix. That covers the dynamic variables (`UUID`, `TIMESTAMP`, ...) and anything `interpolate.rs` reads with a prefix such as `store.`.
- Each rename is listed in the report.

### Secrets

Secret means `variable[].secret: true`, or a variable that ends up as an auth credential (the API key, bearer token or basic password).

Literal credentials count too: any header or query param the curl import would scrub (`Authorization`, `X-Api-Key`, `token`, ...). They're turned into variables with the same naming rules, so the anti-goal holds even for a collection that pasted its key in.

- The CLI writes each secret to `.env` as a commented-out line (`# API_KEY=`), with a comment saying to set it in `.env.local` (gitignored). It never writes the value.
  - The builder checks what the runner does when a secret is left unset and makes the report say so plainly.
- The studio uses the collection's value for a secret when it has one, and offers it through the same "save secrets" path as the curl import. That sends it to the Keychain and marks it secret in the collection notes. A secret with no value is listed as "set this secret". Neither case writes the value to a file.

### Plain variables

Both the CLI and the studio write non-secret variables to the output root's `.env`, adding only missing keys. Requests run from that root, which is where curl-runner loads `.env` from (the current directory) and how the studio runs a collection. The CLI's report and the docs say so.

## CLI

`curl-runner convert postman <collection.json> [-o <dir>]`

- Writes the folder tree and `.env` under `<dir>`, or under a new folder named after the collection in the current directory if `-o` is left out.
- Never overwrites. A taken file name gets `-2`, `-3` and so on, the same rule as the studio's curl import.
- If `.env` already exists, only missing keys are added. A key that's already there with a different value is kept and listed in the report.
- Prints the report to stderr every time: counts (folders, requests, variables), then a short list of what needs attention (files to pick, secrets to set, renames, skipped scripts, unsupported auth and the like). `-o` means a directory here, unlike the other subcommands, so this command gets its own path in `convert_cmd.rs`.
- Exits non-zero only when the input can't be read or isn't a supported collection. Reported items are not failures.

## Studio

The Postman tab in the existing Import dialog replaces its Coming soon state. Everything else in the dialog stays as it is.

This is new UI, not a swap of the Coming soon placeholder. The dialog's `count()` and `write()` only know curl and folder imports today, so the Postman tab needs its own file picker, preview and summary.

- **Choose:** pick or drop a `.json` file, then choose the target folder (default: the open collection's root).
- **Preview:** before writing, show the counts and the attention list from the report, the same way the curl tab shows what it will import.
- **Import:** write through the dialog's existing safe path: create-new only, `-2` suffixes, and the YAML check. Then refresh the tree and open the first imported file, as the curl import does.
- **Summary:** what was imported, plus the attention list. "Pick a file" items should be easy to act on. The builder decides how, for example by opening that file.
- Remove the Coming soon handling for Postman only. OpenAPI and Folder keep it, and the existing test for those tabs keeps passing for them.

## Constraints

- Rust. The converter goes in `curl-runner-core/src/convert/`, next to the curl converter, and the studio's Postman tab calls it.
- It has its own YAML emitter rather than going through `CurlRunnerIr` and `serialize_to_yaml`.
  - That serializer must stay byte-identical to the old TS output, and it sorts headers, params and form fields.
  - The Postman output keeps the collection's order, so disabled lines can sit where they belong.
  - Share small helpers (quoting, value formatting) where it doesn't change the existing output. Existing snapshots must not change.
- Reuse the studio import's helpers where they fit: secret scrubbing rules, file naming and safe writing.
- Every change gets unit tests, plus `cargo fmt`, `cargo clippy -D warnings` and `cargo test --workspace` (AGENTS.md).
- Test inputs are small hand-written collections, inline or under the core's `tests/fixtures/`. Together they must cover the motivating shape described in Why. No real-world collection, name or URL goes in the repo.
- Docs: a "Postman to YAML" section in `features/convert.mdx` (with the CLI reference table updated), and the studio docs no longer list Postman as Coming soon.
- A changeset describing what a user notices.

## Done when

- Converting a collection with the motivating shape gives one YAML file per request in matching folders, the variables in `.env`, and the API key handled as a secret. Every disabled field is commented out in place, and descriptions come through as comments.
- After the user provides the secret values and picks the upload files, each converted request runs with `curl-runner` and sends what the Postman request would send.
- Every unsupported input in the test collections appears in the report.
- The owner imports a real collection locally, outside the repo, and confirms the result.

## Left to the builder

- How files and folders are made filesystem-safe, including collisions between requests with the same name.
- The placeholder path for files that need picking.
- The exact report format, as long as it's short and puts what needs attention first.
- Which curl-runner dynamic variables match which Postman ones.
- How the studio summary links to the items that need attention.
