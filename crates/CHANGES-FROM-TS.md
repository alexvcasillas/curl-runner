# Changes from the TypeScript CLI

Intentional behavior differences between the Rust port and `packages/cli`.
Format: behavior: TS / Rust / reason.

- Non-numeric `CURL_RUNNER_*` numeric values (e.g. `CURL_RUNNER_PROFILE_WARMUP=abc`, `CURL_RUNNER_MAX_STREAMS_PER_HOST=abc`): TS stores `NaN` and still creates the group (`profile {iterations:10, warmup:NaN}`, `connectionPool {...}`) / Rust leaves the field unset and creates no group / NaN is never a usable setting.
- Negative values for unsigned `CURL_RUNNER_*` fields (e.g. `CURL_RUNNER_RETRIES=-1`, `CURL_RUNNER_FAIL_ON=-1`): TS stores the negative number / Rust ignores the variable / typed unsigned model fields.
- Integers overflowing i64 in `CURL_RUNNER_*` values: TS parses to a float / Rust ignores the variable / same reason.
- Prototype-chain lookups in interpolation (`${constructor}`, `${toString}`): TS resolves them via `in` on plain objects / Rust leaves them unresolved (or env/static lookup only) / accidental JS quirk, and a security hazard.
- Non-unicode process env values: TS yields a (lossy) string / Rust treats the variable as unset (`std::env::var`) / Rust API limitation.
- `RANDOM:string:N` with N too large for usize: TS would try to allocate / Rust leaves the reference unresolved / avoid abort.
- `interpolate_request` failures (interpolated value no longer fits a typed field): TS silently keeps going with the raw value / Rust returns an error naming the field / avoid running a request with a literal `${store.x}`.
- `InterpCtx` API: TS reads `process.env` directly / Rust takes an injected env lookup and borrowed maps / testability (no behavior change).
- CLI numeric values that are `NaN` in TS (`--timeout abc`), negative-looking, or overflow u64: TS stores `NaN`/a float / Rust leaves the option unset / typed unsigned fields. (`--keepalive-time abc` therefore no longer force-enables the pool.)
- `config::resolve` takes the process env as an injected lookup and cwd as a parameter for `curl-runner.yaml` discovery: TS reads `process.env`/cwd / Rust is injected / testability (no behavior change).
- Unknown/`=`-style flags: TS silently ignores them (an unknown `--flag` swallows the next non-dash arg) / Rust identical (documented and tested, NOT a deviation; `--flag=value` is unsupported in both).
- Precedence: TS merges each test file's `global` after CLI flags and env vars (file beats CLI) / Rust uses defaults < curl-runner.yaml < test-file `global` < env < CLI / matches the docs (cli-options.md) and the bug policy.
- Per-request precedence: TS lets a test file's `global.defaults` (timeout, retry block as a whole) and `global.output` win over CLI/env flags at request level / Rust layers per request base < file `global.defaults` < `collection.defaults` < CLI/env-derived defaults < the request itself, merges `retry` field-wise (`--retries` and `--retry-delay` never wipe each other or the file's other retry fields), and CLI/env output flags beat the file's `global.output` in `sourceOutputConfig` / matches docs and the bug policy.
- `curl-runner.yaml`: TS reads only `global` (other sections never cause errors) / Rust the same, but a `global` with a wrongly typed field (e.g. `maxConcurrency: abc`) is skipped with a warning (TS would load the raw value) / typed model.
- Request `timeout` units (spec bug fix #1): TS passes the documented millisecond value to `curl --max-time` (seconds), so `timeout: 5000` waited 5000 s / Rust sets `CURLOPT_TIMEOUT_MS = timeout`; dry-run prints `--max-time` in fractional seconds (`5000` -> `5`, `1500` -> `1.5`) / docs say milliseconds.
- Units audit: `connectionPool.connectTimeout`, `connectionPool.keepaliveTime` (seconds), `retry.delay`, `--retry-delay`, `--watch-debounce` (milliseconds) are consistent across types, docs, CLI help and TS usage; no change.
- Transport failures (connection refused, DNS failure, timeout, max-redirs exceeded): TS treats them as success. `executeCurl` fails only when `exitCode !== 0 && !stdout`, and `-w` always writes stdout, so these come back `success: true` with status 0 (or the last 3xx) and are never retried / Rust returns a `TransportError` (failed request, retryable) / bug fix.
- Transport error text (new with the above, TS never showed curl's stderr for these): `Request timeout after {timeout}ms`, or `Connection timeout after {ms}ms` when the pool's connect timeout is the smaller one still running during resolve/connect/TLS, as the docs show; other failures use curl's format `curl: (N) <libcurl message>`.
- Relative formData file, `ssl.ca/cert/key` and `output` paths resolve against the process cwd, as in TS (no deviation; noted because an earlier port draft used the YAML file's directory). Snapshot and baseline directories stay next to the YAML file, as in TS.
- `method: HEAD`: TS runs `curl -X HEAD`, which waits for a body that never comes (hangs until timeout when Content-Length > 0) / Rust also sets `CURLOPT_NOBODY` / bug fix.
- URL globbing: the curl tool expands `{a,b}` / `[1-3]` in URLs into several transfers / libcurl sends the URL literally / globbing was never an intended feature.
- Missing formData files: TS checks in the executor (`File(s) not found: field: path`) / Rust reports the same message from `transport::build_easy` (paths relative to cwd, as in TS).
- Connection-pool options (`keepaliveTime`, `connectTimeout`, forced HTTP/2) apply per handle whenever `connectionPool.enabled` (TS applied them only in parallel mode via the batched executor; sequential runs ignored them); without the pool the curl tool defaults are reproduced (TCP keepalive 60 s, max 50 redirects, `User-Agent: curl/<libcurl version>`).
- HTTPS trust store: the system curl uses its configured CA bundle / the static rustls libcurl has none, so Rust sets `CURLSSLOPT_NATIVE_CA` (OS trust store) unless `ssl.ca` is given / required for HTTPS to work at all.
- Empty strings (`proxy`, `output`, `ssl.ca/cert/key`, file `filename`/`contentType`) are falsy in TS and skipped; Rust skips them the same way (no deviation, noted because `CURLOPT_PROXY ""` would otherwise disable env proxies).
- Path guard (`security::path_guard::resolve_safe`): lexical like TS `path.resolve` plus a prefix check (symlinks are NOT resolved, so a symlink inside cwd pointing outside is not detected, same as TS). Prefix test is component-wise (`/a/bc` is not inside `/a/b`; TS used `startsWith(base + sep)`, equivalent except for a root cwd `/`, where TS rejects everything but `/` itself). Takes `cwd` as a parameter (must be absolute when confining); relative `base_dir` is taken relative to `cwd`. Scope matches TS: `output` and formData files (both relative to cwd) are confined; `ssl.ca/cert/key` are not. A request `output` is now resolved against the injected `cwd`.
- `--output` (save summary) goes through the same guard with `base_dir = cwd` (Task 9 wires it; TS logged `Cannot save results: <error>` and skipped the write).
- URL guard uses the `url` crate (WHATWG, like JS `new URL`), so accept/reject decisions match; the check also runs inside `transport::build_easy`, so `send` is safe on its own (TS only checked in the executor). Order matches TS: paths, then URL.
- Protocol allow-list is also applied with `CURLOPT_PROTOCOLS_STR`/`CURLOPT_REDIR_PROTOCOLS_STR` (TS: `--proto`/`--proto-redir` `-all,<list>`). libcurl rejects a list naming protocols the build lacks, so the list is intersected with the supported ones (an unsupported entry stays blocked). The static libcurl here ships fewer protocols than the system curl tool.
- Redactor: no global singleton; `Redactor` is passed around. Explicit secrets are keyed by value, not by `__req_*_<first 8 chars>` (TS: two tokens sharing their first 8 chars overwrote each other, leaking the first). `api_key=`/`token=`/`secret=` values are replaced by span (TS replaced the first textual occurrence of the value inside the match, so `secret=cret` became `se[REDACTED]=cret`). `Redactor::from_env_vars(vars, false)` registers no explicit secrets but built-in token patterns stay on, as in TS (`--no-redact` only skips `SECRET_*` values). `from_env_vars` takes every `SECRET_*` key of the map it is given (TS: only keys from `.env` files).
- User regexes (`expect.body` patterns, condition `matches`): TS uses V8 `RegExp` / Rust uses `fancy-regex` (lookaround and backreferences work, compiled patterns cached) after translating `\d \w \s \b` (and negations) to JS's ASCII/JS-whitespace meanings, `.` to JS dot (excludes `\r`, `\u2028`, `\u2029`), `\0` to NUL, `[`/`&`/`~` inside classes to literals and a `-` next to a class escape to a literal / not supported: JS-only syntax that fancy-regex rejects (`\cX`, `[^]`, `/.../` flags), which counts as an invalid pattern (no match, as TS does for invalid regexes); the `i` flag uses Unicode case folding (e.g. `ſ` matches `s`, JS does not in non-unicode mode); a pattern that exceeds the backtracking limit counts as no match (TS would hang) / no JS regex engine in Rust.
- `expect.headers` non-string values (e.g. `x-count: 5`, `x-flag: true`): TS always fails (number === string) / Rust stringifies and compares / bug fix.
- Response JSON integers beyond 2^53: TS `JSON.parse` rounds them to the nearest double everywhere (`9007199254740993` -> `9007199254740992`) / Rust keeps the exact digits in the printed body (`--output-format json`/`raw`, `--pretty-level detailed`); the `--output` file, stored values, conditions and snapshots still print JS digits, and YAML-side numbers round like JS / serde_json integer parsing; display only, never less precise.
- `--output` request echo: non-string `expect.headers` values are echoed as strings (`content-length: 5` is saved as `"5"`; TS kept the YAML number) / consequence of the typed string map above.
- Body/store path lookups (`expect.body` keys, `store` paths, condition `store.a.b`): TS resolves inherited properties (`toString`, `hasOwnProperty`, string `length`) via normal JS property access / Rust reads own keys only, plus array `length` and numeric indices (`items.length` works as in TS; `name.length` on a string stays undefined as in TS) / prototype lookups are accidental JS quirks.
- `expect.body` object keys that look like integers: JS iterates them first, so their errors come first / Rust keeps YAML order / only error order differs, never pass/fail.
- `postprocess` API: TS `postProcessResult` is async and calls the snapshot manager / Rust splits it into `apply_validation` and `apply_snapshot` (the snapshot comparison itself belongs to the snapshot port) / no shared mutable manager in core.
- Request loading keeps each merged request as raw JSON until execution (`parser::prepare_raw`, `executor::load_run`): TS types nothing, so behavior matches; a request whose fields don't fit the model after store interpolation (e.g. `timeout: "${store.name}"`) fails with `invalid value at \`timeout\`: ...` instead of TS running it with the raw value. The request merge rules now have one implementation (`parser::merge_request_json`); an explicit `null` in a request now replaces the default like a JS spread (before, the typed merge let the default win).
- `.env` values for `${VAR}`: TS relies on Bun auto-loading `.env` into `process.env` (keyed by `NODE_ENV`) / Rust looks up the process env first, then the `.env` files chosen by the final `env.environment` / no Bun runtime; same precedence (real env beats `.env`).
- Exhausted retries after a transport failure: TS (where curl failures never surfaced) would report `Operation returned retriable result` / Rust reports the transport error (`curl: (7) ...`, `Request timeout after ...`); exhausted retriable statuses keep the TS text `Operation returned retriable result`.
- Parallel runs: TS ran chunks of `maxConcurrency` (each chunk waits for its slowest request) and, on a failure without `continueOnError`, reported every request of the chunks run so far / Rust keeps a sliding window of `maxConcurrency` live requests on one `curl::multi` handle and, on such a failure, stops starting new requests and reports every request already started / throughput. Without a limit (unset, 0, or >= the request count) every request runs and is reported, as with TS `Promise.all`.
- Connection pool (`connectionPool.enabled`, parallel): TS batched one curl process per host (`--parallel-max maxStreamsPerHost`), ignored `maxConcurrency` and `retry`, and marked 4xx/5xx failed before `expect` ran (so `expect.status: 404` or `expect.failure` could never pass) / Rust uses the same multi path as plain parallel runs (retries and `maxConcurrency` apply; `maxStreamsPerHost`, default 10, becomes `CURLMOPT_MAX_HOST_CONNECTIONS`; HTTP/2 multiplexing on) and judges status only through `expect`, as non-pooled TS does; TS pooled also ran every request but truncated the reported results at the first failure in request order (request-executor.ts:503-505), Rust follows the plain parallel rules above / bug fix.
- Dry run also checks formData files exist (TS `validateFileAttachments` ran before the dry-run branch); Rust gets the same `File(s) not found: ...` by building (not performing) the transfer.
- Executor events: TS logged from inside the executor / Rust emits `EventSink` events (`on_start`, `on_command`, `on_retry`, `on_result`, `on_stored`, `on_stop`, each with the 1-based request index); in parallel mode `on_result` fires in completion order (TS pooled logged after all finished, in order). Summary file writing is `executor::save_summary` (returns the `Cannot save results: ...` line instead of logging it).
- Cancellation (new): `Executor::cancel_handle()`; stops starting requests, drops in-flight transfers, and the summary holds completed results only.
- Retry waits (`delay * backoff^n`, `Retry-After`) are clamped to 24 h (`executor::retry::MAX_DELAY_MS`); NaN counts as 0 / TS would sleep for any value (or never return) / avoid overflow panics in `Duration`/`Instant`.
- Errors building a transfer (missing formData file, guard failures inside `build_easy`) fail the request immediately without retries, matching TS, which checked files before running curl; only transfer failures are retried.
- Sequential transfers run on a single-handle `curl::multi` loop reused across requests (connections stay alive between requests; TS spawned one curl per request), so a cancel interrupts an in-flight request. Idle keep-alive connections are held open until the run ends (libcurl's connection cache), so a server sees long-lived idle sockets that TS closed after each request.
- Colors: TS always prints ANSI codes / Rust prints them unless `NO_COLOR` is set to a non-empty value / standard opt-out; lets tests and CI logs be color-free.
- Redaction of printed output: TS applies the full redactor (explicit secrets + built-in token patterns) only to request URLs and curl commands in console output, and to the whole saved results file / Rust does the same with the full redactor, and additionally replaces explicit secrets (`.env` `SECRET_*` values and registered request secrets such as bearer tokens, basic passwords, sensitive header values) in every other printed string (bodies, header values, errors, stored values, names, skip reasons, JSON/raw output) without applying the token patterns / a known secret echoed by a server no longer leaks into CI logs, while token-like strings in bodies stay visible for debugging as in TS.
- File discovery: Bun's `Glob.scan('.')` never matches absolute paths, so `curl-runner /abs/path/test.yaml` found no files / Rust accepts absolute files, directories and globs / bug fix. Other rules unchanged (literal prefix kept as typed, hidden entries skipped by wildcards, sorted, de-duplicated).
- Ctrl-C (new): TS died on SIGINT with no summary / Rust cancels the run (in-flight transfer dropped), prints the summary of completed requests and `✗ Interrupted`, writes `--output` if set, and exits 130; a second Ctrl-C exits 130 at once.
- `--output` file with several test files: TS runs each file as its own group and rewrites the file after each group, so only the LAST file's summary was saved / Rust writes the file once at the end of the run with the aggregate of all files (same `ExecutionSummary` shape; `total`/`successful`/`failed`/`skipped` summed, `results` concatenated in run order, `duration` = sum of the per-file run durations, matching the printed global summary), and also on Ctrl-C with the completed results / bug fix (CI artifacts lost all but the last file). Per-file store and stop-on-error are unchanged; the exit code is computed on the same aggregate, as in TS (`determineExitCode` on `executeRequests`' combined summary).
- `sourceOutputConfig` in the saved results: Rust stores the CLI/env output overrides there at runtime (precedence fix above) but writes each request's file-level `global.output` (`{}` when absent) to the results file, as TS / keeps the file identical.
- Sequential event order: the result is reported before its `Stored: ...` lines, as TS logged them (core `on_result` now precedes `on_stored`).
- Detailed metrics: DNS/TCP times print as missing (0) for requests that reuse a kept-alive connection (TS spawned a new curl per request, so they were always non-zero) / consequence of connection reuse.
- `formatSize` beyond GB: TS printed `undefined` as the unit / Rust keeps `GB` / cosmetic.
- --output JSON key order: TS follows YAML/insertion order / Rust uses a fixed struct order / JSON consumers are order-agnostic.
- `--output` write: TS `Bun.write` writes in place / Rust writes a temp file next to it and renames it over the target (also ignores a second Ctrl-C while saving) / a killed or interrupted run never leaves a truncated results file.
- Request secret registration: same as TS (every request's inline secrets are registered before the run, after file-level interpolation, plus store-resolved values as each request runs); a request whose typed fields cannot be typed before the store resolves (e.g. `timeout: ${store.t}`) has its secrets registered only when it runs.
- Dry run with `store`: TS interpolates `${store.x}` to `""` (nothing is stored in a dry run) in the printed command, URL and body and prints `Stored: x = ""` lines / Rust leaves `${store.x}` literal and prints no `Stored:` lines / the literal shows which values come from earlier responses (controller ruling).
- Snapshots (`snapshot::SnapshotManager`): files and hashes are byte-compatible with TS (`JSON.stringify(data, null, 2)`, no trailing newline; hash = first 8 hex of md5 over the compact `JSON.stringify` of the snapshot object while `hash` is still `""`, so it includes `updatedAt`; key order `hash`, `updatedAt`, `status`, `headers`, `body`; JS number formatting, array-index object keys first). `serde_json` runs with `float_roundtrip` so parsed floats are the same doubles JS gets (the default fast path can be 1 ulp off, which changes the hash). `updatedAt` is `toISOString()` format.
- Snapshot hook API: TS `compareAndUpdate(yamlPath, name, result, config)` / Rust `compare(&RequestConfig, &ExecutionResult, &SnapshotConfig)` (+ `compare_and_update`), returning `io::Result`; the executor hook (`ManagerHook`) maps a write failure to a failed comparison (`snapshot saved` vs `write failed: <error>`) where TS rejected the request / write errors are reported instead of aborting the request.
- Snapshot files that fail to parse (invalid JSON, a lone-surrogate escape like `"\ud800"` that `JSON.parse` accepts but `serde_json` rejects, or no `snapshots` object): TS treats invalid JSON as missing and silently replaces the whole file (or crashes on a wrong shape) / Rust never overwrites such a file: the comparison fails with an error naming the file (also in `--ci-snapshot` and with `-u`) / avoids losing every stored snapshot. Entries are read like untyped JS objects: missing `hash`/`updatedAt` are fine, `status: "200"` stays a string and differs from `200`, falsy entries count as missing. Unknown top-level and per-snapshot fields are preserved on update (the file is edited as JSON, not through the typed model).
- Snapshot load-modify-save: TS parallel requests could race (load was outside the write queue, so one snapshot could overwrite another) / Rust serializes compares behind the executor's hook mutex / bug fix.
- Snapshot output (`NEW`/`PASS`/`FAIL` lines and diffs): same text and colors as TS, but the request name and diff values go through the redactor like every other dynamic string / TS printed them unredacted.
- `include`d `status`/`headers` are kept even when empty, `headers` lowercased and sorted (TS code unchanged); `Snapshot` model fields were reordered (`hash`, `updatedAt` first) to serialize in TS key order.
- Response diffing (`diff::BaselineManager`/`ResponseDiffer`/`DiffOrchestrator`, `curl-runner diff <a> <b> [file]`, `--diff*`): file names, `JSON.stringify(data, null, 2)` bytes (no trailing newline), key order (`hash`, `capturedAt`, `status`, `headers`, `body`, `timing`), hash (md5 of the compact object while `hash` is `""`), labels, `isNewBaseline`, summary text/colors, json/markdown output, exit codes (`diff` subcommand exits `changed > 0`; a normal run is unaffected by diffs) and the quirks (only the first YAML file is diffed, request-level `diff:` is ignored by the post-run flow as in TS, `Summary:  (0 total)`, third raw arg of `diff` is the file even if it is a flag) are identical; output verified byte-identical against the TS CLI (colors included) and baselines TS wrote are read and re-written byte for byte. Timing percent uses JS `toFixed(0)` (ties away from zero, `-0.3` prints `-0`, `Infinity`/`NaN` kept).
- Baseline files that fail to parse (invalid JSON or no `baselines` object): TS treats them as missing, so `--diff-compare <label>` replaced the file with the current run / Rust compares as missing (everything `NEW`) but never replaces such a file: it logs `baseline file ... cannot be used` and keeps it / avoids losing the stored baseline. `--diff-save` still replaces the file, as it replaces any file in TS. Stored entries are read like untyped JS objects (`status: "200"` differs from `200`, falsy entries count as new).
- Baseline writes: TS queued writes per path (`writeLocks`) but `saveBaseline` always replaces the whole file and TS only diffs the first file, so there is no load-modify-save race (unlike snapshots) / Rust writes the same way, no extra serialization needed.
- Diff output goes through the redactor (request names, labels, diff values, also in the json format) / TS printed it unredacted. Write failures abort the diff step with `✗ <error>` and exit 1 (TS threw into the top-level catch, same exit).
- `diff` runs after the results file is written (TS saved it inside `execute`), so `Results saved to` precedes the diff report as in TS. A Ctrl-C skips the diff step.
- `--diff-compare <label>` auto-save: TS treated "every request is new" as "no baseline" and replaced the stored file, which also happened when an existing baseline matched no request name (renamed requests) or when no request succeeded (0 of 0) / Rust saves the run only when the baseline file does not exist; an existing file (or one that cannot be read, see above) is never replaced and the normal summary is printed (`NEW` lines, or `Summary:  (0 total)`) / avoids losing stored baselines.
- Profile mode iterations (`--profile`): TS spawned one curl per iteration with no retries, validation or `when`/`store` / Rust runs the iterations through the shared executor with `expect`, `retry`, `when`, `store` and `snapshot` stripped and never a dry run (`--dry-run` is ignored, as TS's profile path never looked at it), sequentially for concurrency 1 and on the parallel (`curl::multi`) path with a sliding window of `concurrency` live requests otherwise (TS ran chunks that each waited for the slowest) / same results, shared transport code. `--profile-concurrency 0` runs sequentially (TS looped forever).
- Profile failures: a failed iteration is a transport failure (see Transport failures above: refused, DNS, timeout), which TS counted as a successful sample with status 0 / Rust excludes it from the timings and counts it in `failures` (every failed iteration, warmup included) / bug fix. TS `failureRate` was failures / successful samples, which exceeds 100% when most iterations fail (2 failures and 3 successes gave 66.67 rather than 40; all-failed gave 0) / Rust splits the finished iterations by position (the first `warmup` are warmup, the rest measured) and reports measured failures / measured iterations, rounded like TS (`Math.round(x * 10000) / 100`) / bug fix. Warmup is dropped by position, not from the successes. The exit code keeps the TS rule (1 when failures including warmup / iterations run > 50%); the divisor is the number of iterations actually run, so a run where every iteration failed exits 1 and one cancelled before its first iteration exits 0.
- Profile mode is chosen before the test files are read, as in TS: a `global.profile` block inside a test file supplies the settings but only `--profile`/`CURL_RUNNER_PROFILE`/`curl-runner.yaml` switch the mode on (no deviation, noted because the bundled example looks like it should).
- `--profile-export`: TS `Bun.write` resolves the path against the cwd without the path guard / Rust the same; a write error prints `Cannot export profile results: ...` and exits 1 (TS crashed with an unhandled rejection). JSON and CSV bytes are identical to TS. With `--output-format json` the per-request stats lines are compact JSON, as in TS.
- Profile iterations are timed inside the executor (typing, guards and the transfer), not around a spawned process, so latencies exclude process start-up and are lower than TS's / inherent to in-process libcurl. Iterations are handed to the executor in windows of about 256 requests (a multiple of `concurrency`), keeping only (success, duration) per iteration, so memory does not depend on `--profile N`; a window drains before the next starts (as TS chunks did) and sequential windows do not share a connection with the next one.
- Ctrl-C during `--profile` (new): the run stops promptly, prints the stats of the completed iterations and the summary, writes `--profile-export`, prints `✗ Interrupted` and exits 130 (TS died with no output).
- Watch mode (`--watch`): same flow as TS (initial run, `Watching for changes...` lines, 300 ms default debounce in ms, `--no-watch-clear`, one queued re-run for changes during a run logged as `(queued change)`, a failing run never stops watching, Ctrl-C exits 0 silently even mid-run). Differences: Rust watches the parent directory of each file (non-recursive) and reacts to modify/create events on the watched paths, so editors that save by rename-over keep working (TS `fs.watch` on the file itself lost the watch after such a save) / the file list is still the one found at start, files added later are not picked up, as in TS. Each re-run reloads and re-resolves the files from scratch (TS re-parsed only inside `executeRequests`); a reload that fails (bad YAML, no requests) prints `✗ <error>` and keeps watching. Screen clearing only happens on a terminal (as `console.clear`). SIGTERM exits 0 in watch mode only, as TS (a handler registered inside watch mode; a normal run keeps the default SIGTERM behavior). A change that arrives during a run triggers one immediate re-run after it finishes (no new debounce wait), where TS restarted the debounce timer and ran when it fired. If the files cannot be watched a warning is printed and the process stays alive, as TS.
- `convert` (`curl-runner convert curl|file|yaml`): curl -> YAML text, the `--debug` dump, warnings, help, exit codes and the `-o` file are byte-identical to the TS CLI (colors included) for every case in `crates/curl-runner/tests/golden/convert` (recorded from TS by `generate.ts`, replayed by `tests/convert_cli.rs`) and for ~4000 randomized curl commands, scripts and YAML files checked against Bun. The TS quirks are ported as they are, not fixed: a combined boolean token (`-sSL`) skips as many following tokens as it has characters (so `curl -sSL URL` loses the URL), a combined value flag (`-XPOST`) also swallows the next token, `$'..'` is not special, empty quoted tokens vanish, `-F` without a file ignores `--form-string`, the `Authorization` header is dropped when a `Basic` value decodes without a `name:` part, `convert yaml` does no validation.
- `convert`: `generateCurlFromYaml` (typed `RequestConfig` -> curl) is exported by the TS package but used nowhere (the command uses `generateCurlFromIR`) / not ported. The dry-run command (`transport::curl_command`) and the `convert yaml` command (`convert::generate_curl_from_ir`) print different curl lines in TS (flags, `\`-continuations, quoting) so they stay two separate generators.
- `convert yaml` YAML parse errors: TS prints Bun's `YAML Parse error: <Bun message>` / Rust prints `YAML Parse error: <serde_yaml_ng message>` / the text differs, the exit code (1) is the same.
- `convert` JSON bodies (`-d '{...}'`) go through `serde_json`: a lone-surrogate escape (`"\ud800"`), a number out of the `f64` range (`1e999`) or nesting deeper than 128 levels is not JSON for Rust (the body becomes urlencoded/raw text) where `JSON.parse` accepts them / inputs that do not occur in real curl commands.
- `convert` key sorting (`params`, `headers`, `formData` keys) reproduces `String.prototype.localeCompare` (ICU, en-US) exactly for ASCII and for Latin letters with a single accent; other characters (Greek, Cyrillic, CJK, symbols, ligatures such as `æ`/`ß`) sort by code point after the Latin letters, which matches ICU for same-script keys but not for every mix.
- `convert` error messages: a malformed `%` escape in a URL prints `URI error` (what Bun's `decodeURIComponent` throws); missing or unreadable inputs print Node's `ENOENT: no such file or directory, open '<path>'` / `EISDIR: ...` / `EACCES: ...` text, `Directories cannot be read like files` for a directory input; the TypeErrors TS hits on odd YAML (`null` request, missing `url`, non-string `proxy`/`output`/`ssl.*`/`url`, non-iterable `requests`) keep Bun's message text. All exit 1 through the `✗ <message>` line.
- `convert file` / `convert yaml` read the input as UTF-8 with replacement characters (like `Bun.file().text()`); `-o` creates missing parent directories (`Bun.write` does) and then prints `ℹ Written to <path>`.
- YAML integers beyond the `i64`/`u64` range (normal runs and `convert yaml`): read as `f64` like JS (`123456789012345678901234` is `1.2345678901234569e+23`), so they no longer fail to parse.
- `validate` YAML parse errors: Bun reports only `YAML Parse error: <short reason>` (`Unexpected token`, `Unexpected EOF`, `Multiline implicit key`, ...) / Rust prints `Unexpected EOF` when the scanner hit the end of the stream and `Unexpected token` otherwise, so most messages match but Bun's rarer reasons are not reproduced / different YAML parser.
- `validate` on tab-indented YAML that Bun accepts (it reads `request:\n\turl: x` as `{request: null, url: x}`): TS validates the lenient result / Rust reports `Failed to parse YAML: YAML Parse error: Unexpected token` / the Rust runtime cannot load such files, so "valid" would be false.
- Duplicate mapping keys (all commands, shared parser): the last value wins, in the first key's position, as with `Bun.YAML.parse` (was a `duplicate entry with key ...` parse error; bug fix).
- Tab-indented YAML on normal runs: both fail, with different messages (TS reads it leniently and then finds no requests or a wrong shape; Rust stops at the YAML error).
- `validate` header casing for names that are `Object.prototype` members (`constructor`, `toString`, ...): TS looks them up on a plain object and suggests renaming to the function source (`"function Object() {\n [native code]\n}"`) / Rust only knows the real standard headers / JS prototype quirk.
- `validate` file read errors: TS shows Bun's error text after `Failed to parse YAML: ` / Rust shows the OS error text.
- `validate` emulates the `TypeError`s TS throws on unexpected shapes (null document, non-object document, non-iterable `requests`, `null` request/snapshot/diff, non-string enum values, `method`, `when.left`, non-string `Content-Type` with a string body, a non-object `when`, `null` conditions): same message on stderr (`✗ <message>`), exit 1, as the TS CLI's catch-all prints. Messages are Bun's for the TS source (a minified build would name other identifiers).
- `validate --fix` output: TS's emitter could write YAML that no longer parses or changes meaning: empty `{}`/`[]` on the next line at a smaller indent, strings such as `*/*`, `@x`, `&a`, `| x` and keys like `a: b` left bare, and `yes`/`on`/`-1`/`~`/`010` left bare so they re-read as booleans, numbers or null / Rust keeps TS's layout and text wherever TS's output was valid, but writes `key: {}`/`key: []` (and `- {}`/`- []`) inline, an all-holes list as `[]`, and double-quotes (JSON escapes plus `\uXXXX` for characters YAML can't take raw) every string or key that would not read back as itself under the runtime parser / bug fix. A test re-parses every `--fix` output of a mutated corpus and checks it equals the fixed data.
- `validate` multi-document YAML: Bun parses it to an array of documents; Rust does the same for `validate` (`parser::parse_raw_stream`), so the same issues are reported.
- YAML scalars (all commands, shared parser `yaml_load`): plain scalars now resolve exactly like `Bun.YAML.parse` 1.3 (`yes/no/on/off` in lower/Capitalized/UPPER case are booleans, `010` is 10, `0x`/`0o` only in lower case, no `0b`, `_` makes a string, Bun's lenient forms such as `1e` or `--1`, `!!bool`/`!!int`/`!!float`/`!!null` only accept their kind, other tags and quoted/block scalars give strings, merge keys merge like Bun's `MappingProps`); before, YAML 1.2 core rules applied, so `insecure: yes` failed to load and `a: on` in a body was sent as `"on"` / bug fix. Checked against `crates/curl-runner-core/tests/fixtures/bun-yaml/scalars.json` (5275 Bun results). Remaining differences: `.nan`/`.inf` become `null` (JSON has no NaN/Infinity; TS keeps a number until it is serialized, where it also becomes `null`); every number is a JS number, i.e. an `f64` (not a difference: integers beyond 2^53 round to the nearest double as in JS, and are carried as JSON integers with JS's digits, so `1234567890123456789` is sent as `1234567890123456800` and `9007199254740993` as `9007199254740992`, like Bun); Bun ends the document at a plain `---` on an unindented line (`v: ---`), Rust reads the string `---`.
- `validate --fix` on a file whose root is not one mapping (a multi-document file, which parses to an array of documents, or a top-level list): TS rewrote it from that array, erasing the file (it became `"\n"`), and printed `✓ Fixed N issue(s)` / Rust leaves the file untouched and prints `  ⚠ Not fixed: --fix only rewrites a file with a single mapping document` (no `Fixed N` line; the issues still count toward the summary) / bug fix (data loss).
- Number text on the wire and in files (request bodies, `--output` summary): TS uses `JSON.stringify` / Rust used `serde_json`, which printed whole floats as `2.0` and large values in float notation (`1e20`, `1.2345678901234568e+18`) / Rust now prints like `JSON.stringify` (`2`, `100000000000000000000`, `1234567890123456800`, `1e+21`; integer-like object keys first), as snapshots, baselines and `convert` already did / bug fix.
- YAML nesting depth (all commands): more than 128 nested sequences/mappings (aliases included) is a parse error, `recursion limit exceeded: more than 128 nested levels` (the limit `serde_yaml_ng` already applied) / Bun allows deeper nesting and errors somewhere between 1000 and 5000 levels / keeps every recursive walk (conversion, drop, interpolation, validators) far from the stack limit; 100000 levels give a clean error, no abort.
- Other YAML loader differences from `Bun.YAML.parse` (libyaml does the syntax; all pinned in the parity test or listed here): `|+`/`>+` keep chomping at end of input: Bun adds one line break too many (`a: |+\n  x\n\n` is `"x\n\n\n"` in Bun, `"x\n\n"` in Rust, which is what YAML specifies); multiline implicit keys: Bun rejects a flow-collection mapping key (`? [a, b]\n: 1\n? {x: 1}\n: 2` is "Multiline implicit key") and accepts a flow-mapping key broken over lines (`{a\n b: 1}` is `{"a b": 1}`), libyaml does the opposite (`{"a,b": 1, "[object Object]": 2}`, and a parse error); a bare `...` like `---` on an unindented line (`v: ...`) ends the document in Bun (`{v: null}`, or a parse error at end of input), Rust reads the string `...`; a self-referencing alias (`a: &x [*x]`) fails in both, with Bun's `Unresolved alias` vs `serde_yaml_ng`'s `recursion limit exceeded` message.
- Raw U+0085 (NEL), U+2028 and U+2029 in YAML: Bun (YAML 1.2) reads them as ordinary characters / libyaml (YAML 1.1) treats them as line breaks, so inside a scalar they fold to a space or newline (`"o<NEL>p"` -> `"o p"`, `|` block `l1<LS>l2` -> parse error) and in a plain scalar or an indented block they can make the file fail to parse (`invalid YAML: could not find expected ':'`) / libyaml limitation; use the `\N`, `\L`, `\P` (or `\u2028`) escapes in double-quoted strings, which both accept.
- Wizard (`curl-runner init`, `init --wizard`, `edit`): same questions, order, defaults, labels, hints and validation messages as TS, with `cliclack` in place of `@clack/prompts` (look and key handling differ cosmetically: it prints to stderr, a prefilled value is a default taken on an empty answer rather than editable text, so a defaulted optional field cannot be blanked). `init -h` / `edit -h` are byte-identical to TS. The `request:` YAML text the wizard builds is byte-identical to TS (no trailing newline, as TS) for every case in `crates/curl-runner/tests/golden/wizard` (recorded from the TS builder by `generate.ts`), template defaults included. Intro/outro text, `Wizard cancelled` (exit 0) on Ctrl-C and `File not found: <file>` (exit 1) are as TS.
- Wizard YAML where TS wrote text that does not read back as the config (18 of 79 recorded cases, flagged `tsRoundTrips: false` in `cases.json`; each checked by parsing the TS text with `Bun.YAML.parse`): a list whose only item is a one-line mapping or list (`items:   - id: 1`), an empty `{}`/`[]` value (`a:` then `{}` on its own line), the empty string (`password: ` read back as null; the same for an empty key), and plain strings that YAML reads as something else or rejects (`~`, `*/*`, `@x`, `'q'`, `| x`, `!x`, `? x`, `on`, `-1`, `- item`, a `,` inside an inline `[a, b]` list, a key such as `yes` or `010`) / Rust writes `key: {}`/`key: []` inline, starts a list item's list on the next line, and double-quotes (JSON escapes) what would not read back, with the same TS layout and quoting everywhere else. Done through `yaml_text::scalar_text` / `map_key_text`, the helpers `validate --fix` already uses (its read-back check moved there); the only wizard-specific part is which strings TS quoted (`:` `#` newline, leading/trailing space, leading digit, `true`/`false`/`null`/`yes`/`no` in any case), which differs from `--fix` and `convert`. Every YAML text is parsed back and compared to the intended data before it is written; a mismatch refuses to save (exit 1) instead of writing.
- Wizard writes (init, edit, quick init) are atomic (temp file in the same directory, then rename; a symlink is followed and the target replaced, an existing file keeps its permissions, missing parent directories are created like `Bun.write`) / TS wrote in place.
- `edit`: TS rewrote the file as `request:` plus the first request only, so every other request, `global`, `collection` and every request key the wizard has no prompt for (`store`, `when`, `snapshot`, `expect.body`, an `oauth` `auth`, ...) was erased / Rust updates the edited request inside the full document: a key whose value is the same before and after the prompts stays exactly as in the file (including `followRedirects: true` and key order), changed keys are replaced in place, new ones go last, cleared ones are removed, `expect` is merged by `status`/`responseTime`. The file is read with the shared parser (no interpolation) so `${VAR}` is kept as written. A file whose root is not one mapping (a list, a multi-document stream, a scalar), that has no request, or that does not parse is an error (`No request found in YAML file ...` / the parse error, exit 1) and is never written. YAML comments and anchors are not kept (the document is re-emitted; aliases and `<<` merges are expanded), as in TS.
- Wizard prompts: the advanced options set `followRedirects`/`insecure`/`http2` to the answer (TS only ever turned them on or `followRedirects` off, so an edited file could not be switched back); status codes must be whole numbers (TS wrote `NaN` for `200,abc`); a `number` field in the interactive JSON builder that is not a number is kept as a string with a warning (TS stored `NaN`); `init -o <file>` is the default of quick init's `Save to` prompt (TS ignored it there). `Basic` auth with a non-string password in an edited file shows it as text.
- Wizard without a terminal (stdin or stderr not a TTY): TS ran `@clack/prompts` on piped keystrokes (and with `</dev/null` printed the first prompt and exited 0 when the event loop drained; with stdin closed (`<&-`) Bun hangs) / Rust reads one answer per stdin line (empty line: default, select by value or number, confirm `y`/`n`, multiselect comma separated); end of input is a cancel: `Wizard cancelled`, exit 0, nothing written, so it never hangs. Covered by `tests/wizard_cli.rs`.
- `Run request after creating?` / `Run now?` run this executable on the written file (TS: `bun run <cli> <file>`); the child's exit code is ignored, as in TS.
- `upgrade` on a standalone binary (TS: ran `curl -fsSL https://www.curl-runner.com/install.sh | bash`, or the PowerShell script, through a shell): Rust upgrades in-process. It reads the latest GitHub release (`releases/latest`, version from the tag), downloads `curl-runner-cli-<version>-<platform>.tar.gz` (`.zip` on Windows) and `SHA256SUMS.txt` from the `@curl-runner/cli@<version>` tag, checks the SHA-256 before anything else, extracts `curl-runner-<platform>[.exe]` with Rust crates (no `tar`/`unzip`), writes it next to the running executable and renames it over it (Windows: the old file is renamed to `<name>.old` first and restored if the swap fails). Any failure (download, missing checksum line, mismatch, bad archive, no write permission) leaves the binary as it was and removes the temp file; a permission error prints the `sudo curl-runner upgrade` hint. `--dry-run` prints the archive URL and target path instead of the install script line. npm and bun installs run the same commands as TS (`npm|bun install -g @curl-runner/cli@latest`, through `cmd /C` on Windows).
- Install detection (`install::detect`): TS's `curl` and `standalone` sources are one `Standalone`; the TS order and heuristics are kept (`.bun` / `BUN_INSTALL` / `/bun/...` paths, any `node_modules` path, `npm_config_prefix`/`npm_execpath`), so the platform packages (`node_modules/@curl-runner/cli-<platform>/`) of npm, bun, pnpm and yarn are recognized. pnpm and yarn installs are treated as `npm` (the upgrade runs `npm install -g`, as TS did for any `node_modules` path). Added: `~/.local/bin` is checked before the npm env variables (a shell that exports `npm_config_prefix` no longer turns the curl-installed binary into an "npm" install), and a binary under `target/debug` or `target/release`, or with no known path, is `Unknown`: `upgrade` prints how it was detected, says it cannot upgrade and exits 1.
- `upgrade` shares the TS flags (`-n/--dry-run`, `-f/--force`, `-h/--help`) and output; the "Installation:" line shows `standalone binary` for the old `curl installer` source too. The TS version check before the command is not run for `upgrade` (it does its own lookup).
- Update notice (TS `VersionChecker`): same rules (skipped when `CI` is set, 24 h cache in `~/.curl-runner-version-cache.json` in the same format, 3 s timeout, every failure silent, banner text as TS). Differences: the check runs on a thread and the banner is printed after the command ends, waiting at most 300 ms for a lookup still in flight (TS printed it whenever the fetch returned, in the middle of the run output); it only runs when stdout is a terminal, so piped and redirected output is never altered and scripted runs never touch the network (TS also checked there); it is not started for `--help`/`--version`/`upgrade`; in watch mode the process ends on Ctrl-C, so no banner appears.
- Test-only environment variables, not part of the CLI contract: `CURL_RUNNER_TEST_REGISTRY_URL` replaces the npm registry URL (version check and `upgrade` for npm/bun) and `CURL_RUNNER_TEST_GITHUB_BASE` replaces both `https://api.github.com` and `https://github.com` (the repo path is appended), so tests use the testkit server instead of the network. TS had no such hooks.
- Hardening of the update paths (new): the `CURL_RUNNER_TEST_*` URL overrides are only read in debug builds or with the `test-hooks` cargo feature, release binaries ignore them; an https download never follows a redirect to http; the temp file of a binary swap is created with `create_new`; a GitHub release tag without `x.y.z` is "Failed to fetch latest version" (TS fell back to the raw tag); a binary inside a Homebrew `Cellar` or `~/.cargo/bin` is `Unknown` (never self-replaced); the version check records its attempt in the cache before the lookup, so a slow or failing registry is tried once per 24 h (TS only cached after success).
- `validate` key lists follow the config model (bug fix vs 1.x, which warned `Unknown key` for supported keys, #136): `global.env` and `global.security` are known blocks (`environment`, `redactSecrets`; `allowedProtocols`, `allowPaths`); `profile` also takes `histogram` and `exportFile`; `snapshot` takes `enabled`, `name`, `include`, `exclude`, `match`, `dir`, `updateMode`, `ci`; `diff` takes `enabled`, `exclude`, `match`, `includeTimings`, `dir`, `label`, `compareWith`, `save`, `outputFormat`; `retry` takes `retryableStatuses`. Keys the model does not have are now warned: `profile.percentiles`, `snapshot`/`diff` `ignoreFields` and `ignoreHeaders`, `diff.baselineUrl` (the runner ignored them). Side effect: an array `snapshot` now suggests `ci` for the index key `0`, so two `edge` golden lines changed. Request-level `snapshot` takes `enabled`, `name`, `include`, `exclude`, `match` and `diff` takes `enabled`, `exclude`, `match`, `includeTimings` (the runner ignores `dir`, `updateMode`, `outputFormat` etc. there, so they are now warned as unknown); the larger lists above are `global.snapshot` / `global.diff`. The `edge` goldens changed accordingly.
- `validate` accepts interpolated numeric values (bug fix vs 1.x, which reported `timeout: ${TIMEOUT}` and similar as errors, #137): any numeric field the validator checks (request `timeout`, `maxRedirects`, `retry.count`/`delay`/`backoff`, `global.maxConcurrency`, `profile` iterations/warmup/concurrency, `connectionPool` numbers, `watch.debounce`, `ci.failOn`/`failOnPercentage`, `expect.status` (scalar or array element), and the same fields under `defaults`) is skipped when its string value contains a `${...}` reference (detected with the interpolator's `extract_variables`), since the value is only known at run time. Plain non-numeric strings and out-of-range numbers still error. Any string containing a `${...}` reference is accepted for these fields (resolved at run time; the runner interpolates `expect.status` too).
- `convert curl` request bodies go in the YAML directly (bug fix vs 1.x, #138): 1.x wrote `-d '{"a":1}'` as `body: { json: { a: 1 } }`, which the runner then sent literally as `{"json":{"a":1}}`. Now objects and arrays are the `body` value, so the converted file sends the original JSON; non-JSON `-d` data (raw or urlencoded) is a plain string `body`, and a JSON scalar (`0`, `null`, `"s"`) is a string holding its JSON text (a bare `null`/`0`/`false` body would send nothing). Keys such as `on`/`no`/`null` are quoted so they do not read back as booleans. `convert yaml` (YAML to curl) still reads `json:`/`form:`/`raw:`/`binary:` bodies from older files, and a plain string `body` now gives `-d 'text'` (1.x gave `-d '"text"'`). Known limit: a JSON object body whose only key is `json`, `form`, `raw` or `binary` reads back through `convert yaml` as that body kind.
- `convert curl` string bodies (follow-up to #138): `-d`/`--data`/`--data-raw`/`--data-binary`/`--data-urlencode` text without an explicit `Content-Type` gets `Content-Type: application/x-www-form-urlencoded` in the YAML, which is what curl sends (the runner alone would default a body to JSON). String bodies are quoted/escaped so they always read back identically (multi-line text, `- a`, `#x`, ...; 1.x wrote such text raw and produced invalid YAML). `--data-binary @file` bodies are now plain strings (the text `@file`, not a file read), and on the YAML to curl path a plain string `body` no longer gets the `Content-Type: application/json` header that 1.x added (1.x also quoted it as JSON, `-d '"text"'`).
