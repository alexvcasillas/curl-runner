<Callout type="warn" title="Private preview">
curl-runner Cloud is in private preview. Sign-ups open at launch. Until then the dashboard and the commands on this page talk to a server that only accepts people we have invited. You can also [run the server yourself](/docs/self-hosting).
</Callout>

Cloud keeps a copy of your collection where your team and your customers can open it. Git stays the source of truth. Your CI publishes the folder on every push, and Cloud shows the latest version.

- **Publish** a folder of YAML files from CI with `curl-runner publish`.
- **Manage** it in the dashboard: teams, tokens, versions, members and billing.
- **Share** it with a link, or with named people.
- **Pull** a shared collection onto your machine with `curl-runner pull`.

## What leaves your machine [#privacy]

Publishing sends the YAML files in the folder, the `cloud:` name, description and inputs, and the git commit, ref and repository when your CI provides them. That is all.

Secret values never leave your machine. A secret input is declared by name only. Its value is set by whoever runs the collection, on their own machine. `publish` refuses to send a folder where a secret input has a literal value in a `variables` block (`global`, `collection` or top level).

Files over 1 MiB, and folders over 2,000 files or 25 MiB, are refused.

## Declare the collection [#config]

Add a `cloud:` block to `curl-runner.yaml` in the collection folder:

```yaml title="curl-runner.yaml"
cloud:
  collection: payments-api
  name: Payments API
  description: Smoke tests for the payments service.
  inputs:
    - name: BASE_URL
      description: Where the API runs.
      default: https://api.example.com
    - name: API_TOKEN
      description: A token for the staging API.
      secret: true
      required: true
```

| Key | What it does |
| --- | --- |
| `collection` | The collection's slug. Lowercase letters, digits and dashes, up to 63 characters. Required. |
| `name` | A display name, 1 to 100 characters. |
| `description` | Up to 500 characters. |
| `inputs` | The values a person fills in before running the collection. |

Each input has these keys:

| Key | What it does |
| --- | --- |
| `name` | Letters, digits and underscores, not starting with a digit. Required. |
| `description` | Shown next to the input. |
| `secret` | Hides the value. Defaults to `true` for names that start with `SECRET_`, else `false`. |
| `required` | The collection can't run until it is set. Defaults to `false`. |
| `locked` | The person running the collection can't change it. Defaults to `false`. |
| `default` | A starting value. A secret input can't have one. |

If a non-secret input has no `default`, the value of the variable with the same name in `collection.variables` or `global.variables` is used.

## Publish from CI [#publish]

```bash title="Command"
curl-runner publish
```

```text title="Output"
payments-api: published v3 (1 added, 2 changed, 0 removed)
```

`publish` checks every file on your machine first and sends nothing if anything is wrong. An unchanged folder is not published again:

```text title="Output"
payments-api: unchanged (v3)
```

```bash title="Options"
curl-runner publish [DIR...] [--collection <slug>] [--team <slug>] [--server <url>] [--dry-run]
```

| Option | What it does |
| --- | --- |
| `DIR...` | Folders to publish. Defaults to the current folder. Each folder is one collection. |
| `--collection` | Overrides `cloud.collection`. Works with one folder. |
| `--team` | The team to publish to. Falls back to `CURL_RUNNER_TEAM`. |
| `--server` | The API URL. Falls back to `CURL_RUNNER_SERVER`, then `https://api.curl-runner.com`. |
| `--dry-run` | Checks the files and shows what would change. Sends nothing. |

The token comes from `CURL_RUNNER_TOKEN`, or from the session that `curl-runner login` saved. A publish token (`crt_...`) belongs to one team, so you must give it a team. A signed-in account that is in one team needs no `--team`.

Publishing records the commit, ref and repository from GitHub Actions or GitLab CI, so each version links back to git.

### Exit codes [#exit-codes]

| Code | Meaning |
| --- | --- |
| `0` | Published, or nothing to change. |
| `1` | Invalid files, or a bad option or `--server`. Nothing was sent. |
| `2` | Not signed in, the token can't publish to that team, or the team is suspended. |
| `3` | Your plan's limit was reached. |
| `4` | The collection's source is the studio, not git. Switch its source to git, then publish again. |
| `5` | The server could not be reached. |

`publish` tries a request up to five times, waiting longer each time, before it exits with `5`.

With more than one folder, a refusal from the server for one folder does not stop the others. Each failure is printed with its collection, and the exit code is the most severe one: `5`, then `2`, `4`, `3`, `1`. An unreachable server stops the run at once.

A config file named `.curl-runner.yaml` is not published, so `publish` stops with exit `1` and asks you to rename it to `curl-runner.yaml`.

`login`, `logout`, `publish` and `pull` all exit `1` for a bad option, a missing value or a bad `--server`. Exit `2` is only for sign-in and access problems.

### GitHub Action [#github-action]

The repo ships a composite action that installs the CLI and runs `publish`.

```yaml title=".github/workflows/publish.yml"
name: Publish to curl-runner Cloud

on:
  push:
    branches: [main]

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: alexvcasillas/curl-runner/actions/publish@main
        with:
          token: ${{ secrets.CURL_RUNNER_TOKEN }}
          team: acme
          path: collections/*
          version: 2.6.0
```

| Input | Default | What it does |
| --- | --- | --- |
| `token` | none | The publish token. Required. Keep it in a repository secret. |
| `team` | none | The team slug. Required. |
| `path` | `.` | Folders to publish, separated by spaces. Globs such as `collections/*` expand. |
| `server` | `https://api.curl-runner.com` | The API URL. Set it for a self-hosted server. |
| `version` | `latest` | The `@curl-runner/cli` version to install. Pin the current release, as in the example. |

<Callout type="warn" title="Pin it">
`@main` moves with every commit. For a workflow that holds a token, pin the action to a commit SHA, such as `alexvcasillas/curl-runner/actions/publish@<full-commit-sha>`, and pin `version` too.
</Callout>

Any other CI works the same way. Install the CLI, set `CURL_RUNNER_TOKEN` and `CURL_RUNNER_TEAM`, and run `curl-runner publish`.

## Sign in [#sign-in]

Open the dashboard at `https://cloud.curl-runner.com`. On a self-hosted server it is the `PUBLIC_APP_URL` you set. There is no password. Continue with GitHub or Google, or enter your email and type the 6-digit code we send. You can also click the link in the same email. A code works for 10 minutes.

GitHub and Google show up only when the server has them set up. Email always works.

To sign in to the CLI with the same account, run `curl-runner login --browser`. It opens the dashboard sign-in page. After you sign in, the page shows a code. Paste it into the terminal.

```bash title="Command"
curl-runner login --browser
```

If the browser doesn't open, open the printed link yourself. Without `--browser`, `login` emails you a code and you type it in the terminal. Run `curl-runner login --server <url>` for a self-hosted server.

## Create a team [#team]

A team owns collections, tokens and members. Choose **New team** from the team switcher, or let the dashboard send you there after your first sign-in. Enter a name and a slug, such as `acme`. The slug is part of every URL and can't change later.

Who can create a team depends on the server. On the hosted service you can. On a self-hosted server, `SIGNUP` decides. See [Self-hosting](/docs/self-hosting#signup). If you can't create a team, you can still open collections that people shared with you.

## Create a publish token [#tokens]

A publish token belongs to one team and can only publish. Open **Tokens** and choose **Create token**. Give it a name, such as `github-actions`, and an expiry. Never, 30 days, 90 days or 1 year.

<CloudScreenshot name="tokens-created">The token shows once. Copy it into your CI's secrets as `CURL_RUNNER_TOKEN`.</CloudScreenshot>

The dialog also shows the GitHub Actions step to paste into your workflow. Revoke a token from the same page. Revoking one doesn't affect the others.

## Publish [#publish-dashboard]

Publish from CI as described in [Publish from CI](#publish). The first publish creates the collection. Open it from the **Collections** page to see these tabs:

- **Versions** lists every version, who published it, the commit, and the file count. **Changes** shows a diff against the version before it. The download icon gets a zip of that version.
- **Inputs** lists the inputs from the `cloud:` block. A secret input never shows a default.
- **Settings** switches the collection's source between git and the studio, downloads the current version, and deletes the collection. Only owners can delete.
- **Sharing** opens the share settings.

<CloudScreenshot name="collection">A collection with two versions. Each publish makes a new one.</CloudScreenshot>

## Share a collection [#share]

Open a collection and choose **Share**. Pick who can open the link:

| Access | Who can open it |
| --- | --- |
| Off | Only members of your team. |
| Public | Anyone with the link. No account needed. |
| Restricted | Only the people on the access list, after they sign in. Needs the Team plan. |

<CloudScreenshot name="sharing">Restricted access, with an email and a whole domain on the list.</CloudScreenshot>

The page shows the share link with a **Copy link** button. You can set it to expire, or **Reset link** to replace it and stop the old one working. A reset can't be undone.

In Restricted mode, add an email, or `*@example.com` for everyone on a domain. Leave **Email them the link** checked to send an invite. Domains never get an email. Each entry shows whether the person has opened the link yet. **Remove** takes someone off the list.

<Callout type="warn" title="A link is a credential">
Whoever holds a share link can use it. In Public mode that means anyone. Don't paste it where you wouldn't paste a password. If a link leaks, reset it.
</Callout>

**Preview the page** shows what your customers see.

## Members [#members]

Open **Members** to invite people. Enter an email and a role, then **Send invite**. An invite expires after 7 days.

| Role | What it can do |
| --- | --- |
| Member | Publish, share collections and create tokens. |
| Owner | Everything a member can do, plus manage members and billing, and delete collections. |

<CloudScreenshot name="members">Two members and one pending invite.</CloudScreenshot>

Owners change a role from the list or remove a member. Anyone can leave a team, except its only owner. To leave a team you own alone, make someone else an owner first, or delete the team. Customers you share with are not members and never use a seat.

## Billing [#billing]

On the hosted service, a team starts on the Free plan. Free has up to 3 members, counting pending invites, with unlimited public collections and publishing. The Team plan has no member limit and adds Restricted sharing. It costs $10 per member per month, or $96 per member per year. Prices are in USD before tax.

Owners open **Billing** to see the plan and the member count, and to upgrade. **Upgrade to Team** goes to a Stripe checkout page that accepts business tax IDs. After you pay, the page shows the new plan. To change the interval, update the card or cancel, use the Stripe customer portal from the same page. A cancelled team goes back to Free at the end of the period. If a payment fails, a banner on every page tells owners, and Stripe retries the charge. If you don't update the card within 14 days, the team moves to Free.

Nothing is deleted when a team moves to Free. Restricted collections keep serving the people already on their list. Until you upgrade again, or switch those collections to Public or Off, you can't publish to a Restricted collection, add people to it, or add members past 3.

Stripe Tax adds tax at checkout.

Members can see the plan but can't change it. A self-hosted server has no plans. The page doesn't exist there, and every feature is on.

## Shared with me [#shared-with-me]

**Shared with me** in the header lists the collections people shared with you, from every team. You see it even if you aren't in a team. Each row has **Open in studio** and the `curl-runner pull` command to copy.

## What your customers see [#landing]

A share link opens a page with the collection name, the team, the request count and the latest version. If the link is Restricted, the person signs in first.

<CloudScreenshot name="landing">The page behind a Public share link.</CloudScreenshot>

From there a customer can:

- **Open in curl-runner studio**, which opens the collection in the studio.
- **Download the studio** for macOS.
- Run the `curl-runner pull` command shown, on any system.

They fill in the inputs on their own machine. Secret values never go back to your team.

<Callout type="info" title="API">
Everything the dashboard does is also an API call. Sessions and tokens go in `Authorization: Bearer ...`. See `GET /v1/me` on your server for the teams your account is in.
</Callout>

## Open it in the studio [#studio]

This needs the latest curl-runner studio on macOS.

To open a shared collection, choose **Open in curl-runner studio** on the link's page. You can also paste the link into the studio: **Open a shared link** on the welcome screen, or ⌘L. Both link forms work: `https://cloud.curl-runner.com/s/<token>` and `curl-runner://open?server=<api-url>&share=<token>`.

The studio shows the collection name, the team, the request count and the version. A Public collection opens at once. A Restricted one asks you to sign in first. **Sign in** opens the sign-in page in your browser. Once you're signed in, the browser sends you back to the studio, and the collection opens. You sign in once per server, and the studio keeps the session in your macOS Keychain.

Next comes a short form with the collection's inputs. Secret values go into your Keychain, never into the collection folder, and never back to the team. **Add to my studio** saves your copy and opens it.

### Updates [#studio-updates]

The studio checks for a new version when you open the collection, every 15 minutes while it's open, and when you choose **Check for updates**. When there is one, a banner shows the version, when it was published and how many requests changed. **What changed** lists the files added, changed and removed. **Update** brings your copy up to date. Saved secrets and filled-in values carry over. If the new version needs a new input, the studio asks for it in the same short form.

### Your changes [#studio-edits]

Your copy is yours to edit. If you changed files and a new version comes out, the banner says how many. Updating replaces those files. To keep your work, choose **Keep my changes as a copy** first. It saves your edited copy as a separate collection in a folder you pick. Then update the shared one.

## Pull a shared collection [#pull]

If someone shared a collection with you, pull it:

```bash title="Command"
curl-runner pull https://cloud.curl-runner.com/s/<token> payments-api
```

```text title="Output"
Pulled Payments API v3 into payments-api. Fill in payments-api/.env (see .env.example), then run: cd payments-api && curl-runner --all
```

The files are written into the folder. Pulled secret inputs are listed in `.env.example` without values. Copy it to `.env` and fill them in. Run the collection from inside the folder, so its `.env` and `curl-runner.yaml` are used and nested folders are included.

To get the latest version later, run `pull` in that folder:

```bash
curl-runner pull payments-api
```

```text title="Output"
Updated Payments API to v4.
```

If you changed a pulled file, `pull` asks before replacing it. Without a terminal, it stops and tells you to pass `--force`.

```bash
curl-runner pull [LINK] [DIR] [--force]
```

A share link can also look like `curl-runner://open?server=<api-url>&share=<token>`. It names the server itself, so `pull` doesn't have to look it up. Use it for a self-hosted server.

A collection that isn't public asks you to sign in. Run `curl-runner login --server <url>` first, or let `pull` offer it in a terminal. A `pull` writes nothing until every file passes the same path checks `publish` uses, so a bad bundle can't write outside the folder. Exit codes: `0` ok, `1` a problem with the link, the data or an option, `2` sign-in, `5` the server can't be reached.
