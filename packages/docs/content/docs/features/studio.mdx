curl-runner studio is a macOS desktop app for the request files you already have. It opens a folder of YAML as a collection, validates as you type, runs one request or the whole collection, and shows every check, retry and timing.

<Callout type="info" title="Preview">
The studio is a preview. It works fully on local YAML files. Sign in to [curl-runner Cloud](/docs/features/cloud) to publish and share your collections and open the ones teams share with you. Two-way sync from the studio is coming soon.
</Callout>

## Install [#install]

You need macOS 12 or later. The app is a universal build for Apple silicon and Intel, signed and notarized.

Download `curl-runner-studio-<version>.dmg` from the [downloads page](/downloads), open it and drag the app to Applications. Or install it with Homebrew. Homebrew asks you to trust third-party taps before it installs from them, so trust the tap first:

```bash title="Terminal"
brew trust alexvcasillas/tap
brew install --cask alexvcasillas/tap/curl-runner-studio
```

## Your first request [#first-request]

On first launch, choose **Get started**. Welcome then offers **Run your first request**, a short walkthrough that creates `~/curl-runner/getting-started/health.yaml`, a request to `https://api.curl-runner.com/health`, and runs it. The file is never overwritten, so you can edit it freely. To replay the walkthrough, use **Help › Walkthrough**.

## Collections are folders [#collections]

A collection is a folder of request files, and its subfolders are the groups in the sidebar. The studio reads and writes plain YAML, so the files stay the ones [`curl-runner`](/docs/cli-commands) runs in a terminal or in CI.

Run a single request, or the whole collection from **Run collection**. The run screen counts passed, failed, skipped and retried requests, and **Re-run failed** runs only the failures again.

## Live validation [#validation]

The editor runs the same rules as [`curl-runner validate`](/docs/features/validate) while you type. Problems are underlined and listed in the Problems panel, and many of them come with a quick fix.

<StudioScreenshot name="editor-quick-fix" onStudioPage>An unknown key, with the rename it suggests.</StudioScreenshot>

## Responses and checks [#inspector]

The inspector next to the editor shows the last response: body, headers and timing, and each check from the request's [`expect`](/docs/features/response-validation) block.

<StudioScreenshot name="inspector" onStudioPage>A passing request and its seven checks.</StudioScreenshot>

When a check fails, the Checks tab shows the expected and the actual value, a diff of the response body against what was expected, and the [retry](/docs/features/retry-mechanism) timeline with every attempt.

## Environments and secrets [#environments]

Environments come from the collection's [`.env` files](/docs/features/env-files): **Default** reads `.env`, and an environment such as **Staging** reads `.env.staging` on top of it. Variables named `SECRET_*`, and any you mark as secret, are masked. The values you enter in the studio go to the macOS Keychain rather than the files, and secrets are never shared or synced.

<StudioScreenshot name="environments" onStudioPage>The Staging environment of a collection.</StudioScreenshot>

## Import requests [#import]

Choose **File › Import Requests…** or press ⌘I to bring in requests you already have. You can paste curl commands, pick a Postman collection or an OpenAPI spec, or copy a folder of YAML. You see what will be added before anything is written, and no existing file is overwritten.

### Postman collections [#import-postman]

On the **Postman collection** tab, choose a collection you exported from Postman as `.json`, or drop the file on the dialog. The preview lists the request files you'll get and what needs your attention. Secret values go to the macOS Keychain, never into a file.

<StudioScreenshot name="postman-import" onStudioPage>Five requests in two folders. Two things need you before they run.</StudioScreenshot>

After the import, the dialog lists what still needs your attention. Choose **Open** next to a "Pick a file" item to open that request and set the file.

<StudioScreenshot name="postman-import-summary" onStudioPage>After the import. **Open** goes to the request with a file to pick.</StudioScreenshot>

See [Postman Import](/docs/features/postman-import) for what's converted and the full list of what can need your attention.

### OpenAPI specs [#import-openapi]

On the **OpenAPI** tab, choose an OpenAPI 3.0, 3.1 or Swagger 2.0 file as `.json`, `.yaml` or `.yml`, or drop it on the dialog. You get one request file per operation, in a folder per tag. The base URL and the secret names go to `.env`.

<StudioScreenshot name="openapi-import" onStudioPage>Six operations in three tags. Two things need you before they run.</StudioScreenshot>

The importer never copies a secret's value, so the summary lists each secret for you to set in **Environments**.

<StudioScreenshot name="openapi-import-summary" onStudioPage>After the import. **Open** goes to the request with a file to pick.</StudioScreenshot>

A file dropped on either tab is routed by its content: a spec opens the OpenAPI tab, anything else the Postman tab. See [OpenAPI Import](/docs/features/openapi-import) for what's converted and the full list of what can need your attention.

## Run history [#history]

Runs are kept on your machine for 30 days. Pick one to compare it with the run before it: which requests it fixed, which it broke and which got slower.

## Sharing and sync [#sharing]

Sign in from the title bar or **Settings › Accounts & sync**, with curl-runner Cloud or a [self-hosted server](/docs/self-hosting). The avatar in the title bar shows your account and your teams; the status bar names the server. To open a collection someone shared with you, use **Open in curl-runner studio** on its page, or paste the link with ⌘L.

### Publish [#publish]

**Publish**, at the foot of the sidebar or in the palette (⌘K), does what [`curl-runner publish`](/docs/features/cloud) does, signed in as you. The first time, pick the team and the collection's name (suggested from the folder). The studio runs the same checks as the CLI on your Mac, YAML errors and secret values in the files included, and sends nothing until they pass. `.env*`, dotfiles and anything in `.gitignore` stay out.

Leave **Save the name and description to curl-runner.yaml** on to write a `cloud:` block, so CI publishes to the same collection. After that, Publish asks nothing. The sidebar foot says where the folder stands: **Published v14 · 2 hours ago**, or **3 files not published** when the folder has changed since.

### Share [#share]

Once a folder is published, **Share** (at the foot of the sidebar, in the palette, or the title bar's **Shared · N**) sets who else can open it, the same settings as the dashboard's Sharing page:

- **Off**: only your team.
- **Public**: anyone with the link, no account needed.
- **Restricted** (Team plan): only the people on the list, after they sign in. Add an email or a whole domain like `*@globex.com`, and optionally email them the link.

On curl-runner Cloud, a public collection with a `description` in its `cloud:` block can also be listed in the [gallery](/collections) with **List in the gallery**; making it Off or Restricted takes it out.

Copy or reset the link, and set it to expire in 7 or 30 days. Moving a public collection to Restricted asks first, since people using the link who aren't on the list stop getting updates. What people fill in is the `inputs` of the `cloud:` block in `curl-runner.yaml`; values and your Keychain never leave your Mac.

### Sync with your team [#sync]

The first time you put a folder on Cloud, pick how it stays up to date:

- **Publish versions**: the folder is the source. You publish from the studio or from CI. This is the default in a git repo.
- **Sync with my team**: Cloud is the source. Teammates open it in their studio, and every save syncs both ways. Outside a git repo the sidebar's button reads **Put on Cloud** and this is the default.

A synced collection's sidebar foot shows its state (**Synced just now**, **Offline · 3 changes waiting**, **1 conflict · Resolve**) and the last change, such as `v27 · sam@acme.dev edited 1 h ago`. Your saves go up a moment later. Teammates' changes come down on open, on **Sync now**, and at the interval in **Settings › Accounts & sync › Check for team changes** (1, 5 or 15 minutes, or only on open). When a file changed on both sides, the conflict screen shows both versions and asks which to keep.

To open a team's synced collection on another Mac, use **Open from Cloud…** in the palette, the Welcome screen, or a team in the account menu. It makes a folder under `~/curl-runner/{team}` (or one you pick) and syncs it. Collections published from files are listed but open from their repo.

Team owners can switch a collection between Publish and Sync in its settings (**General › Cloud**) or on the dashboard. Switching to Sync makes CI publishes fail; switching to Publish stops syncing for everyone.
